# ADR-001: k6 with TypeScript for load testing

- Status: accepted
- Date: 2026-11-01

## Context
Load tests must live in the repository as code, run in CI with pass/fail gates, model an open workload
(requests arrive whether or not the system keeps up), and export metrics to the same stack that watches the
system under test. The rest of the portfolio is TypeScript and Python.

## Decision
Grafana k6 **2.3.0**, run as the official Docker image, scripts in **TypeScript** (k6 runs `.ts` natively),
type-checked with `@types/k6` and linted with typescript-eslint.

## Alternatives considered
| Option | Pros | Cons | Why not |
|---|---|---|---|
| JMeter | Mature, GUI, protocols beyond HTTP | XML test plans are hard to review in Git; heavy JVM | Code review and CI gates matter more here |
| Gatling | Strong DSL, great reports, open model | Scala/Java/Kotlin toolchain; different language | Would add a fourth language to the portfolio |
| Locust | Python, easy to start | Closed model by default; Python GIL limits load per process | Arrival-rate (open) model is native in k6 |
| **k6** | Scripts are code in TS; arrival-rate executors; thresholds as exit code 99; Prometheus remote write; one binary/image | JavaScript runtime is not Node (no npm packages at run time) | **Chosen** |

## Consequences
- `scripts/k6.sh` runs any scenario in Docker on the shop's network; no local k6 install is needed.
- Thresholds are the gate: breached SLO → exit code 99 → CI fails.
